# OpenCode v2 database fields and lifecycle

Research for [#2](https://github.com/ysm-dev/opencode-stats/issues/2), under [map #1](https://github.com/ysm-dev/opencode-stats/issues/1). Investigated 2026-10-01. This records storage facts, **not dashboard metric definitions**; OpenCode's built-in `opencode stats` was not used.

## Direct answer

Use **`session_v2` for sessions and current metadata, `session_message` for transcript activity and step/tool facts**, joining `project` and, where applicable, `worktree`/`workspace`. Ignore the legacy `session`, `message`, and `part` tables for current activity after migration has completed. Do not equate the transcript's summed usage with session counters: forks copy usage-bearing history without copying counters, reverts remove history without subtracting counters, and title generation adds counters without an assistant transcript row. The optional `event` log is **not guaranteed to exist as retained history**: persistence defaults to false. [S1][S3][S4][S7][S8][S9][S10]

Everything in the field map except exact first-token latency and fresh line-addition/deletion totals can be read as allowlisted scalars/counts **without returning message content to opencode-stats**. SQLite must still read/parse the big JSON strings internally; this is not a content-free physical scan. Do not `SELECT data`, return whole JSON objects, or decode OpenCode message objects in the stats store ingestion process. [S1][S2][S11]

## Lifecycle contract for ingestion

### Inserts and updates

- **Sessions:** `session.created` inserts `session_v2`; rename, metadata/permission changes, agent/model switches, moving and project-identity adoption update it. Agent/model/location switches also append typed transcript messages. The session's selections/location are current values, not immutable historical dimensions. [S3]
- **Admission versus delivery:** `session_inbox` holds pending input only. Admission inserts, queue/steer changes update delivery, delivery/cancellation delete. Delivered user/synthetic messages use the inbox ID but the **delivery event timestamp**, not original enqueue time. Manual compaction/move input does not itself become a user message. The projection and deletion share the event transaction. [S3][S15]
- **Assistant steps:** a started step inserts an empty-content assistant with agent/model/start/snapshot. Durable block start/end and tool state events rewrite its `data`. Text/reasoning deltas and tool progress are ephemeral, not persisted incremental text in this projection. Terminal events attach finish/error, usage and completion/snapshot. A failed step can have no recorded usage at all. The whole JSON row is updated; tools are not independently indexed rows. [S3][S6][S22][S24]
- **Retries/resumption:** a started event for an already-known assistant ID resets its start, stream/completion/error/finish/retry fields rather than adding a second row. A newly starting assistant can forcibly complete the prior incomplete one without supplying finish/usage. Thus “completed exists” is not proof of a successful provider settlement, and created time is not universally immutable. Current retry metadata is an observation of present state, not a count of all attempts. [S6][S16]
- **Shells and compactions:** insert at start, update to terminal status. A compaction terminal event without an existing running row can append a terminal row; failed/ended compactions retain only a created time in their message. Compaction changes model-facing history selection, **does not delete earlier transcript rows** in the current projector. Query all `session_message` rows rather than the API's compacted context view. [S3][S6][S10][S11]
- **Usage counters:** apply increments, not replace with transcript totals. Assistant end/eligible failure adds usage; title/each compaction call adds usage via `session.usage.recorded`. Compaction terminal message repeats the combined usage but does not add it again. Counter writes explicitly preserve session `time_updated`. [S3][S9][S10]
- **Transactions and optional events:** projectors execute inside the bus transaction, together with sequence reservation and optional log insertion. `event_sequence.seq` advances even when `event` payload persistence is false. `event.type` stores a version suffix (`.1` for the cited definitions), `event.created` is epoch milliseconds, and `event.data` is the encoded **payload directly**, not a nested event envelope. Default retention is false; neither an empty log nor missing migrated log entries indicates zero activity. [S4][S24]

### Deletes, reverts and forks

- **Session removal:** OpenCode interrupts/waits, recursively removes `parent_id` children, publishes deletion, then removes the session's aggregate log/sequence. Deleting `session_v2` cascades to `session_message`, inbox, pending and instruction state via foreign keys. Fork relationships are not cascading parent relationships; deleting an origin can leave a surviving fork's origin pointer unresolved. Legacy history is not deleted by this v2 path. [S1][S3][S4][S7]
- **Staged revert:** sets session revert metadata without deleting rows; clear removes that metadata. Committing deletes messages with `seq >= boundary.seq` and inbox entries enqueued at/after that sequence, clears revert and resets instruction state. **Session usage counters are not decremented.** Do not count a staged hidden suffix as already deleted. [S3][S30]
- **Individual message removal:** the current v2 service exposes no independent arbitrary-message-delete writer in the inspected source; native message deletion is the committed revert suffix (and session cascade). Migration can also replace an entire session's projected messages. Do not assume tombstones exist in the OpenCode database. This is a scoped source finding, not a guarantee against a future API/schema change. [S3][S7][S8]
- **Fork copy:** origin and before/through boundary are recorded separately from `parent_id`. Copy settled assistant/shell/compaction history up to the boundary, preserve its sequences/timestamps/data, create IDs of the form derived fork-event ID plus original sequence, reserve copied sequence range, initialize **all counters to zero**. Active projections stay on the origin. Counters after creation track new fork activity, whereas copied transcript usage still looks historical. There is no per-row “copied from message” column; copied-ID construction and fork boundary are source facts, not a license to guess on unrecognised schemas. [S3][S14]
- **Import:** OpenCode can import settled messages and counters directly. Message created times are retained, sequences reassigned, row updated times default to import time; session creation is restored and session `time_updated` becomes import time. Fork provenance is not carried by this import insertion path. This can insert old-created rows today. The dashboard itself will not provide import/export features. [S12]

### Migrated v1 data and stale tables

The migration copies session metadata into `session_v2`, transforms legacy message/part content into current `session_message` shapes, and writes `kv` key `migration.v1-v2` with phase `completed` after finishing. It does **not** keep legacy `session`, `message`, `part` synchronized with v2 activity, or drop those legacy tables in the ordinary transform path. They are migration input/leftovers, not a second activity source. A pre-split v2 lineage is handled separately by renaming its canonical `session` table in place. Therefore table names alone are not sufficient schema recognition. [S8][S31]

Material differences that downstream logic must retain:

- User ordinary/synthetic text can become separate rows; legacy subtask-only wrapper messages can be omitted. Unsupported/invalid/orphan rows produce warnings and are skipped. Message ordering is reconstructed by creation time/ID then numbered densely. [S8] (lines 222–379, 437–489)
- Assistant agent/model/tokens/cost are mapped, missing variant becomes `default`, unsupported finish becomes `unknown`, and snapshots/files are mapped where present. **No `time.streamed`** is invented. If a legacy assistant has a completion time, the migration writes new JSON completion from legacy SQL **`time_updated`**, not the old JSON completion value. This is only a migration proxy for true step end. [S8] (lines 380–435, 1030–1036)
- Legacy completed compaction pairs are folded into a completed compaction message **without model/tokens/cost**; incomplete or errored pairs are omitted. Its assistant usage still participates in migrated session counters. Session counters sum **all decoded legacy assistant messages**, not only transformed retained assistant rows. A historical per-model/time breakdown cannot necessarily reconcile to those counters. [S8] (lines 278–313, 457–487)
- Completed/error tools retain name/call ID, state and start/end timings. Historical names are preserved (for example `bash`, `task`, `apply_patch`), not renamed to v2 names. Running/pending legacy tools become interrupted error states; no `ran` timestamp or `executed` flag is created. Treat these absences as missing capability. [S8] (lines 899–949, 951–1004)
- Migration clears old retained events on first entry and replaces each migrated session's projection. Sequence state is seeded from migrated messages; it is not a complete durable event ledger for historical data. Missing project identity can be reassigned to the global project. Revert and compacting state are cleared. A separate prior-v2 import copies its already-projected JSON as-is. [S8] (lines 534–695, 729–837)

## Timestamp reliability and bucketing

| Timestamp / cursor                                    | Reliable meaning                                                                                                                                                | Not a reliable meaning                                                                                                                                           |
| ----------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `session_v2.time_created`                             | Stored session creation time (preserved by migration/import; newly forked session gets fork time).                                                              | Time of all activity in the session.                                                                                                                             |

| `session_v2.time_updated`                             | Session recency for selected metadata changes and admitted input.                                                                                               | All descendant/message changes: token/cost, viewed/idle transitions, execution claims, project adoption explicitly pin it; many message rewrites don't touch it. |

Sources: timestamp codec/defaults [S5][S32], projector writes/copies [S3], retry reset [S6], import [S12], dispatch/stream/settlement [S16][S24], execution claims [S27], migration [S8], event replay fallback [S4].

**Ingestion requirements, not a metric decision:** retain row identity and replace previously derived facts on update; support removal/reconciliation when rows disappear; separately track new old-timestamp copies/imports and in-place active-row updates; keep missing-field flags; never gate message scans solely on session `time_updated`. Store UTC milliseconds and convert to local-calendar bucket boundaries for dashboard queries, rather than treating a UTC date as the user's local day. No database timestamp supplies the user's timezone. These are implications of the storage contract above, not a prescribed sync implementation.

## Size and empirical verification

### Measurement context (applies to every number in this section)

Run date **2026-10-01**; installed OpenCode **2.0.18**, inspected source commit above; **macOS 26.6.2 (25G83), Darwin 25.6.0, arm64, Apple M4, 16 GiB RAM**. `uname -a` was run (hostname omitted here): kernel `xnu-12377.161.14~5/RELEASE_ARM64_T8132`. `sysctl -n machdep.cpu.brand_string hw.memsize` supplied CPU/memory. Probe: **Python 3.14.5, SQLite 3.53.1** with `ENABLE_DBSTAT_VTAB`; schema inspection CLI **SQLite 3.51.0**. No SQLite tuning was applied.

**Method:** `cp -c` copied `.db`, `-wal`, `-shm` in one command into the approved scratch directory. Copies are sequential, **not an atomic filesystem snapshot**; `PRAGMA quick_check` on the clone returned `ok` (75.457 s), which checks structural consistency but does not prove a transaction-perfect live capture. Main probe used a single explicit read transaction on `file:…/opencode-v2.db?mode=ro`. A follow-up read-only connection checked page/migration/summary counts against the same unchanged clone. The active OpenCode database was not checkpointed, written, or held in a long read transaction. Clone files were deleted after research.

All counts below are aggregate `COUNT(*)` or `SUM` of scalar-presence comparisons; JSON sizes use **`SUM(length(CAST(column AS BLOB)))`** (UTF-8 bytes, not characters); page sizes use SQLite `dbstat`, and free pages use read-only `pragma_page_size`, `pragma_page_count`, `pragma_freelist_count`. Nothing returns prompts, response blocks, tool input/output, project identities, titles, or cost values. Timings use `time.perf_counter()` around execute/fetchall, **one run each**, sequentially after quick-check, on a concurrently used machine; cache state was uncontrolled. They are probe timings, not latency targets or independent cold benchmarks.

Page pragmas reported **4,336,639 pages** of **4,096 bytes**, including **2,056,454 free pages**: **8,423,235,584 bytes (47.42%)** are reusable free-list space. ## Content boundary and extraction examples

The following SELECTs demonstrate the boundary; they are not an ingestion implementation or benchmark promise:

```sql
SELECT id, session_id, type, seq, time_created, time_updated,
       json_extract(data, '$.model.providerID') AS provider,
       json_extract(data, '$.model.id') AS model,
       json_extract(data, '$.model.variant') AS variant,
       json_extract(data, '$.agent') AS agent,
       json_extract(data, '$.tokens.input') AS input,
       json_extract(data, '$.tokens.output') AS output,
       json_extract(data, '$.tokens.reasoning') AS reasoning,
       json_extract(data, '$.tokens.cache.read') AS cache_read,
       json_extract(data, '$.tokens.cache.write') AS cache_write,
       json_extract(data, '$.cost') AS cost,
       json_extract(data, '$.time.streamed') AS streamed,
       json_extract(data, '$.time.completed') AS completed,
       json_extract(data, '$.finish') AS finish,
       json_extract(data, '$.error.type') AS error_type,
       json_extract(data, '$.error.status') AS error_status,
       json_array_length(data, '$.snapshot.files') AS changed_files
FROM session_message WHERE type = 'assistant';

SELECT m.id AS message_id, j.key AS ordinal,
       json_extract(j.value, '$.id') AS call_id,
       json_extract(j.value, '$.name') AS name,
       json_extract(j.value, '$.state.status') AS status,
       json_extract(j.value, '$.executed') AS provider_executed,
       json_extract(j.value, '$.time.created') AS created,
       json_extract(j.value, '$.time.ran') AS ran,
       json_extract(j.value, '$.time.completed') AS completed,
       json_extract(j.value, '$.state.error.type') AS error_type
FROM session_message AS m, json_each(m.data, '$.content') AS j
WHERE m.type = 'assistant' AND json_extract(j.value, '$.type') = 'tool';
```

`json_each` constructs block values **inside SQLite**; no block value is in either result. Never replace the second query's scalar projection with `j.value`. Trust-boundary validation must check the returned types against the recognised schema; arbitrary provider/plugin metadata is not implicitly allowed. [S1][S2]

Forbidden payloads include `text` (user/synthetic/system/skill/text/reasoning), attachments' bytes, shell command/output, tool `state.input` and `state.content`, error message/response body, compaction summary/recent/providerContext, provider states, instructions, patch strings and arbitrary metadata. None was returned by the probe. A recorded cost is an allowed numeric field for the private dashboard/stats store but **not for public research output**. [S2][S25][S28]

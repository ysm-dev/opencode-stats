# Preferences storage at a loopback origin

Research for [#26](https://github.com/ysm-dev/opencode-stats/issues/26). Verified 2026-10-04.

## Scope and evidence

The target is a browser-only dashboard at `http://127.0.0.1:22439`. Its two small preferences are colour scheme and single-key shortcuts enabled/disabled. A different port is a different origin. The page must know its scheme before its first paint. These are the supplied product constraints, not findings about an existing dashboard implementation.

Evidence is browser-engine source, engine-owner documentation, specifications, and OpenCode source/published code. **Verified-in-source** means inspected code or a byte comparison. **Documented** means an official document or specification. Neither label means tested in a shipping browser. Engine snapshots are WebKit `5d643104e491bd71dc72eaaf0d52dbfdef918360`, Chromium `eb3a4bb42677ae222f49978904037b64093dc000`, and Firefox `d0f18859d99ecb16f4c5d641b35a5f3bdb7b4f36`, all dated 2026-10-03. OpenCode is V2 at `d9d094a54378a8af4852a6c3594e0a8a91e2d498`. [Engine-pins] [U-theme]

The OpenCode checkout was read-only. No OpenCode database was opened. The exact npm package was installed in a separate temporary folder with install scripts disabled. Only this findings file belongs to the research branch.

## 1. Safari / WebKit ITP

### Does loopback escape ITP?

**Verified-in-source: `127.0.0.1` does not escape the inspected ITP deletion logic.** `PublicSuffixStore::topPrivatelyControlledDomain()` returns an IP address unchanged. `RegistrableDomain` uses that result, not DNS resolution or the destination socket address. Thus the ITP domain is the string `127.0.0.1`, independent of port. The observer records HTTP main-frame interaction; it excludes `about:`, `file:` and empty URLs, not loopback IPs. [W-domain] [W-observer]

`ResourceLoadStatisticsStore::shouldSkip()` has a conditional check for the exact string **`localhost`**, not IPs or all loopback addresses. It only skips when `ShouldIncludeLocalhost::No` and not running a test. The inspected class defaults that flag to **Yes**. This is not evidence that ordinary Safari always exempts even literal `localhost`. The deletion exemptions are app-bound domains, managed domains, host-configured persisted domains and a standalone application's domain. There is no automatic IP/loopback exemption in that set. [W-skip] [W-exempt]

A WebKit regression test uses **`http://127.0.0.1:8000`**. Its expected output deletes localStorage, IndexedDB and client-written cookies while retaining both ordinary server-written and HttpOnly cookies. This is source/test evidence, not a fresh run of the test. [W-test]

### Seven days: documented policy versus current code

**Documented:** ITP 2.1 (2019) capped persistent `document.cookie` cookies to seven days. Its announcement explicitly excluded HTTP-response cookies and session cookies. The March 2020 announcement extended removal to IndexedDB, localStorage, sessionStorage, media keys, service-worker registrations and cache after **seven days of Safari use without interaction**. It did not require tracker classification for this first-party storage rule. WebKit's current tracking-prevention page still describes the seven-day policy. [W-2019] [W-2020] [W-policy]

**Verified-in-source: do not describe current WebKit as an unconditional seven-day timer.** The inspected implementation has short **7-operating-day** and long **30-operating-day** windows. With first-party removal enabled, `shouldRemoveAllButCookiesFor()` chooses short only for `DataRemovalFrequency::Short`; otherwise it chooses long. Link decoration from a prevalent resource can schedule short removal when it was not filtered. The ordinary first-party path is long. The 2024 change introducing this distinction explains the usability motivation. The loopback test without link decoration expects deletion at 30 days. [W-windows] [W-frequency] [W-change] [W-test]

These facts support **“subject to inactivity deletion, not guaranteed durable”** for this IP origin. They do not establish the exact seven-versus-30-day behavior of every Safari version a dashboard user might run. The public docs and source disagree on the simple seven-day description. [W-policy] [W-frequency]

### Interaction and cookies

**Documented:** a click, tap or keyboard entry counts as user interaction. Scrolling does not. The counter concerns Safari-use days, not seven elapsed calendar days. Merely loading a dashboard or reading it is not a documented interaction. [W-policy] [W-2020]

**Verified-in-source:** interaction updates the main-frame domain's most-recent interaction timestamp. Expiry compares that timestamp with operating-date windows. New interaction therefore renews the inactivity protection. It is domain-level, not port-level: other interactive pages on `127.0.0.1` can refresh the same ITP interaction record. A storage write alone is not the interaction update in this path. [W-domain] [W-observer] [W-expiry]

**Verified-in-source:** modern Cocoa deletion, with `JS_COOKIE_CHECKING` enabled, distinguishes cookies marked `SetInJavaScript`. In script-written-only mode it skips cookies without that mark. The loopback test preserves a non-HttpOnly server cookie as well as an HttpOnly server cookie. Thus **server-written versus script-written**, not merely **HttpOnly versus readable**, matters. The 2022 change aligned client-written cookie deletion with the other script-writable storage and removed the general seven-day fixed-expiry cap in that implementation. The old 2019 announcement must not be treated as the full current implementation. [W-cookie] [W-test] [W-align]

**Documented:** server-set cookies are not generally subject to that script-storage inactivity rule. WebKit does separately cap HTTP-response cookies for third-party CNAME/IP cloaking, and can delete all data for classified trackers. Those are different mechanisms; they do not document a blanket server-cookie cap for a plain same-host loopback dashboard. Cookies still have their own expiry, user clearing and eviction rules. [W-policy] [S-cookie]

### Does `navigator.storage.persist()` help?

**Documented:** Safari 17 added full Storage API support. Best-effort localStorage is within WebKit's storage-pressure/overall-quota eviction policy. Persistent origins are excluded from that eviction. Grants use heuristics such as standalone/Home Screen use; calling `persist()` is not a guarantee. [W-storage]

**Verified-in-source:** WebKit grants `persistOrigin()` only if the domain is already in the set exempt from ITP deletion. Otherwise it returns false. That set comes from the host-configured exemption lists above. Calling `persist()` does **not** itself add an ordinary loopback page to ITP's exemption set. The API is not an independent way to override ITP for this normal browser-tab dashboard. Exact Safari host heuristics for this origin were not runtime-tested. [W-persist] [W-exempt]

The complete client enum lists file system, IndexedDB, service-worker cache, service worker and background fetch. QuotaManager's pressure-driven bucket eviction therefore is not evidence that it evicts localStorage. ### User settings and private windows

- **Verified-in-source:** Chrome's session-only cookie policy is also its storage session-only policy. `StoragePolicyObserver` sends purge-on-shutdown updates; DOMStorage deletes the affected origins during shutdown unless session state is explicitly being kept. **Documented:** Chrome now labels the corresponding options as on-device site data: allow, delete when all windows close, or do not allow. This is broader than third-party-cookie blocking. [C-shutdown] [C-data]
- **Verified-in-source:** Firefox's shutdown sanitizer clears `CLEAR_COOKIES_AND_SITE_DATA`, which includes DOM storage. **Documented:** its “Delete cookies and site data when Firefox is closed” option enables that behavior, with site-specific exceptions. Therefore neither browser's cookie is a workaround for a user's site-data-clearing setting. [F-clear] [F-sanitize]
- **Verified-in-source:** a Chrome localStorage access goes through the content-settings manager's cookie/storage permission check. A denied getter throws `SecurityError`. Firefox denies storage for reject-all-cookie behavior unless a site permission allows it, and its localStorage getter throws `NS_ERROR_DOM_SECURITY_ERR` on denial. The HTML Standard explicitly permits the getter to throw for a storage policy decision. **Catch access to the property itself**, not just `getItem()`/`setItem()`. Blocking only third-party cookies is not equivalent to blocking this top-level first-party dashboard's storage. [C-access] [F-access] [S-storage]
- **Verified-in-source:** Chrome has an in-memory DOMStorage mode. **Documented:** Incognito temporarily keeps site data and deletes it when **all Incognito windows** close. First-party localStorage is available subject to storage permissions; Incognito is not inherently a `SecurityError`. [C-private] [C-incognito]
- **Verified-in-source:** Firefox exposes private localStorage in its private storage scope. QuotaManager observes `last-pb-context-exited` and clears private-browsing storage. It is available subject to permissions and discarded when the last private context exits, not durable across private sessions. Do not infer its on-disk implementation from the older “keeps data in memory” comment: current LSNG has a distinct private repository and cipher-key plumbing. [F-private]

## 3. Cookies, ports and tab synchronization

**Documented:** RFC 6265 §1 explicitly says cookies for one host are shared across all its ports. §8.5 says cookies do not provide port isolation. The retrieval algorithm checks domain/path/security, not the setting port. The current 6265bis draft repeats the rule, including for `__Host-` cookies. [S-cookie] [S-bis]

Thus a host-only, unexpired cookie set at `127.0.0.1:22439` with `Path=/` can also be sent to **`127.0.0.1:4096` and every other port on that IP**, subject to ordinary cookie/request rules. Changing only the dashboard port does not separate or invalidate the cookie. A narrower Path restricts paths, not ports; it is not a security boundary. `HttpOnly` hides the value from scripts, not from another local server receiving Cookie headers. The cookie need not contain sensitive information for this to be an unwanted sharing boundary. [S-cookie] [S-bis]

Cookies are not forever storage. With neither Max-Age nor Expires they are session cookies. Even a specified lifetime is a maximum, not a retention promise. The 6265bis draft recommends a maximum lifetime of 400 days and permits a shorter limit. This is draft guidance, not proof of each browser's exact cookie lifetime implementation. [S-cookie] [S-bis]

**Documented:** HTML's storage-broadcast algorithm excludes the `Storage` object that made the change and queues `storage` events for other same-origin windows. localStorage is shared across same-origin tabs. It is not restricted to the same top-level tab as sessionStorage is. Same-origin includes scheme, host and port: a port change gets separate localStorage and no cross-port `storage` notification. Rewriting the same value does not broadcast a change. [S-storage] [S-origin]

### Pre-paint script

**Verified-in-source:** `packages/app/index.html:19` loads `/oc-theme-preload.js` as a classic synchronous head script, before the root and module entry. `packages/app/public/oc-theme-preload.js:1–33` immediately reads the scheme/theme, queries the OS scheme when `system`, and sets root theme/mode attributes, background and theme-color. For non-`oc-2` themes it injects cached CSS into `#oc-theme-preload`. This is separate from ThemeProvider, not functionality importing the provider automatically supplies to another app. [A-prepaint]

The preload has **no try/catch** around localStorage access. A getter/read failure aborts it before the scheme is applied. It has no runtime theme-ID validation; an unrecognized scheme takes the light branch. It returns early for `oc-2` instead of installing cached CSS. These are limits of copying the existing pre-paint implementation as-is. [A-prepaint]

### Other app settings and server settings

**Verified-in-source:** `packages/app/src/settings/model.tsx:134–145,270–274` defines general, appearance/fonts, keybinds, permissions, workspace defaults, notifications and sounds, then calls `persisted({ key: "settings.v3" }, ...)`. In the **web app**, `runtime/persistence/storage.ts:485–520` selects direct localStorage for this target. The JSON key is exactly **`settings.v3`**, not `opencode.global.dat:settings.v3`. Theme/scheme are separate provider-owned keys. The appearance controller delegates scheme selection to `theme.setColorScheme`. [A-settings] [A-storage] [A-controller]

Named persistence targets use **`<storage-name>:<key>`** in the browser. Constants are `opencode.global.dat` and `opencode.window`; other helpers create workspace/draft/window namespaces. These `.dat` names are **localStorage prefixes in the web app**, not evidence of server files. `runtime/platform/web.ts:5,66–85` separately keeps the default server URL under **`opencode.settings.dat:defaultServerUrl`**. [A-storage] [A-web]

The persistence adapter schema-decodes and normalizes JSON before hydration. Its direct/prefixed localStorage adapters put actual getter/method access inside try/catch and use an in-memory cache/fallback after storage failure. Quota recovery can evict other keys beginning **`opencode.`**. This cannot restore persistence after denied storage or clearing. It is different error handling from ThemeProvider. [A-storage]

`runtime/persistence/persist.ts:5–23,50–80` batches saves with a 100 ms delay, flushes when hidden/pagehide and on owner cleanup, and synchronously hydrates when using synchronous storage. Cross-window synchronization is optional: `storage.ts:633–646` only supplies BroadcastChannel synchronization when `config.sync` is true. **The settings.v3 call does not request it.** ThemeProvider's unconditional storage listener must not be generalized to all settings. [A-persist] [A-storage] [A-settings]

The desktop branch can use `platform.storage(...)`, with host-owned namespace storage; `runtime/persistence/namespace.ts:1–35` specifies its bulk-read/bulk-write driver and revision tracking. That is not what the normal browser app uses. Some settings UI does use server configuration: `settings/general/controllers.ts:26–68` reads `sdk.api.config.get()` and writes **shell selection** with `sdk.api.config.update({ shell: ... })`. Therefore “OpenCode keeps all settings only in localStorage” would also be too broad. The inspected browser appearance/shortcut preferences are local; server shell configuration is separate. [A-namespace] [A-storage] [A-controller]

## Not verified

- No shipping Safari run through seven/30 operating days. Exact Safari-version policy and host-owned persistence grant heuristics remain **unknown**. The source does not support a loopback-IP durability exemption. [W-frequency] [W-persist]
- No real full-disk, shutdown, cookie-blocking or private-window experiment. Browser results above are source/documentation findings, not measured loss probabilities.
- No guarantee that latest engine source is already shipped in every desktop browser. In particular Chromium's 400-day scan is a source fact, not an assertion about all historical Chrome versions. [C-stale]
- No blanket Firefox expiry found; tracker-specific purging exists. This is not an exhaustive audit of every extension, enterprise policy or browser cleaner. [F-ls] [F-purge]
- No opencode-stats preference-file implementation was evaluated. Its own files would be outside these browser stores; their delivery before first paint, write permissions, concurrent writes and corruption handling need a separate design. No browser-storage finding settles that implementation question.

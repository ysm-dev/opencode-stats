Research for [#25](https://github.com/ysm-dev/opencode-stats/issues/25), verified **2026-10-03**. These are implementation facts, not a dashboard accessibility commitment or a WCAG conformance audit. No OpenCode database was opened.

## 1. TanStack Charts 0.18.0, Solid

### Default SVG and accessible information

The ordinary SVG renderer emits one root with `role="img"`, `aria-roledescription="chart"`, `aria-label`, and **`tabindex="0"` by default**. `ariaLabel` is a **required string**, not a generated name: omitting it in the untyped fixture threw inside string escaping. Optional `ariaDescription` becomes a `<desc>`; the ordinary renderer does **not** emit `<title>`, `aria-describedby`, or `aria-activedescendant`. Ordinary bar/line/cell/dot marks have no per-mark role, label or tabindex from this serializer. Focus-guide layers are `aria-hidden="true"`. Opt-in controls such as interactive legends/brushes/zoom have their own semantics; that is separate from ordinary marks. [C-svg] [C-types] [C-controls]

With three synthetic bars, Chromium's initial snapshot was `img "Default chart"`. Native CDP reported `image`, name `Default chart`, `focusable: true`, `roledescription: chart`; it did not expose individually named data marks. The named/described second chart's native AX node had description `Three synthetic bars`, supplied through `<desc>`. A chart without the tooltip extension has no default live data announcement merely because a mark is visually focused. [Spike] [C-tooltip]

### Keyboard model

- Tab focuses the **SVG itself**, not each mark. On first SVG focus, the renderer chooses the first navigable point and updates its internal focus/visual presentation.
- **Right/Down** advance; **Left/Up** retreat; **Home/End** choose first/last. These are linear point navigation, not inherently a two-dimensional grid. Without a custom focus navigation strategy, order compares screen `x`, then `y`, then scene index; endpoints clamp rather than wrap. A selected focus strategy can supply a different navigation order.
- **Enter/Space** activate the current internal point, call `selection.change(point, "keyboard")` and `onSelect`, and can toggle tooltip/cursor pinning when configured. **Escape** dismisses a pinned interaction/cursor state. It is not an unconditional dismissal of every transient tooltip.
- DOM focus stays on the SVG. `onFocusChange` describes library focus, not movement of `document.activeElement` among bars. `keyboard: false` disables point-navigation handling, but does not itself change root tabindex. [C-events] [C-nav]

The spike produced `focus:1 → focus:2 → focus:3 → select:3` for focus, Right, End, Enter, while `document.activeElement.tagName` stayed `svg`. With the tooltip extension enabled, CDP additionally reported **`status`**, name `x: 2 y: 20`, `live: polite`, `atomic: true`; the image name itself did not change. The default tooltip uses `role="status"`/`aria-live="polite"`; structured content's name joins title and `label: value` rows while visible rows are ARIA-hidden. A pinned **custom-body** tooltip instead becomes a nonmodal `role="dialog"` and loses its live attribute. This establishes supplied semantics, not what any particular screen reader speaks or whether browse-mode arrows reach JavaScript. [C-tooltip] [Spike]

### Replacing or hiding output

There is **no ordinary `accessibility: false` option** in the inspected chart props. Supported seams include `tabIndex`, `definition.keyboard`, `definition.pointer`, optional tooltip configuration, custom `renderSvg(scene, options)`, and `onRender({svg, interaction, ...})`. The custom SVG serializer must still produce an `svg.ts-chart` root. The Solid adapter does not spread arbitrary DOM `aria-*` props onto that root; it passes adapter options to the renderer. [C-solid] [C-types] [C-surface]

Thus a custom `renderSvg` can emit `aria-hidden="true"` and `tabIndex={-1}` can remove the SVG tab stop, while callbacks or the exposed interaction controller remain available. Mutating the SVG in `onRender` is also possible, but reconciliation subsequently uses the renderer's markup; it is not an automatic durable accessibility override. **Hiding only the SVG does not hide the separate tooltip/live status or host controls.** The spike hid the SVG and blurred it, and its already-visible `status "x: 3 y: 30"` initially remained in the snapshot. Omitting the tooltip extension removes that default tooltip output. [C-surface] [C-solid] [C-tooltip] [Spike]

### Pointer/touch activation

The **ordinary mark renderer does not inspect `pointerType`** in its pointer-move/down/click path. `pointermove` updates transient point focus. `pointerdown` establishes pointer ownership and updates a free cursor if present; **point selection/`onSelect` runs on `click`, not pointerdown**. There is no ordinary mark `pointerup` selection listener. Touch therefore uses the browser's resulting click event; the base path does not offer a separate touch-selection policy. This is not true of every optional controller: the separate handle/cursor implementations distinguish touch from other pointers, and dragging controllers have down/move/up behavior. [C-events] [C-touch]

## 2. TanStack Hotkeys 0.10.1 / Solid 0.12.1

### Runtime disable and remapping

The core managers have **per-registration** `enabled`/`setOptions`, registry stores, unregister, and destructive `destroy`; neither exposes a reversible registry-wide `setEnabled`/pause switch. Singles and sequences use **different managers**. `SequenceManager.resetAll()` clears partial sequence progress; it does not disable shortcuts. [H-manager] [H-sequence]

Solid can nevertheless turn inherited bindings off with **one shared runtime signal**: `createHotkey`/`createHotkeySequence` accept reactive option accessors, or a `HotkeysProvider` can supply reactive **nested getters** for both default option families. This is a policy propagated into registrations, not an unconditional registry-wide override; a binding that explicitly supplies `enabled` overrides the provider default. The provider captures the initial `defaultOptions` object; replacing that prop wholesale is not equivalent to the nested-getter pattern. [H-solid] [H-provider]

```tsx
const [enabled, setEnabled] = createSignal(true);
<HotkeysProvider
  defaultOptions={{
    hotkey: {
      get enabled() {
        return enabled();
      },
    },
    hotkeySequence: {
      get enabled() {
        return enabled();
      },
    },
  }}
>
  <Bindings />
</HotkeysProvider>;
```

Verified with one `J` binding and one `U,V` sequence inheriting these defaults: enabled fired both; `setEnabled(false)` left both counters unchanged; re-enabling fired both again. The directly shared-accessor pattern also disabled bare `G`, `Shift+G` and `G,P` together. [Spike]

**Remapping is supported at the registration layer.** Solid accepts a hotkey accessor or a sequence accessor and unregisters/re-registers when their resolved strings change. Core registration handles update callbacks/options, not the registered chord itself. Recorder primitives capture chords/sequences, but there is no library-owned user settings UI or persisted action-to-binding map. Changing the fixture's accessor `G → X` made X invoke the same callback. [H-solid] [H-manager] [H-recorder] [Spike]

### Sequences, Shift and input/screen-reader interaction

- `createHotkeySequence(['G', 'P'], ...)` represents `g` then `p`; bare uppercase **binding spelling is not a Shift requirement**. `Shift+G` explicitly requires Shift. Letter matching normalizes case but still compares Shift exactly. Printable nonletter glyphs have an implicit-Shift allowance, e.g. producing a symbol is not treated identically to Shift+letter. [H-match]
- Sequence timeout defaults to **1,000 ms**. Modifier-only events, repeating keydown and IME-composing events do not advance it. A wrong step can restart at the first step if that key matches it; otherwise partial progress resets. Prevent-default/stop-propagation occur on completing a sequence, not on every partial prefix. Registering both `G` and `G,P` can invoke the single G action **and** later the sequence; the spike observed both. [H-sequence] [Spike]
- Default `ignoreInputs` is true for bare keys and Shift/Alt chords, but false for Ctrl/Meta chords and Escape. Sequences derive this default from their **first step**. Explicit `ignoreInputs: true` can suppress modified shortcuts too. Input detection includes **all input types except button/submit/reset**, textarea, select and contenteditable, the active element and composed event path. An input that is itself the registration's explicit `target` is exempt from this filter. All document-target navigation bindings in the fixture stayed silent while its text input received `g`, `p`, `x`, `Shift+G`. [H-defaults] [H-input] [H-sequence] [Spike]
- No screen-reader detection or browse-mode integration exists in the inspected matching/event path. The callback runs only if a matching DOM keyboard event reaches its target and passes these checks. A screen reader intercepting a key before the page sees it cannot trigger that callback; a screen-reader-focused ordinary button is not automatically considered an input. No spoken-output or screen-reader key interception test was performed. [H-manager] [H-input] [H-match]

### Tooltip and WCAG 1.4.13

The published UI explicitly sets **`closeDelay={0}`**, **`ignoreSafeArea` default true**, and closes its uncontrolled state on trigger pointer-leave if focus is not inside the trigger wrapper. Its stylesheet applies **`pointer-events: none` to tooltip content**, including the shared base used by all appearances. Kobalte itself has safe-area/hover-content logic, but the wrapper and CSS do not preserve that capability by default. [U-tooltip] [K-tooltip]

Chromium observed: hover opened the tooltip; it remained open after 1.2 seconds with stationary hover; Escape dismissed it without moving the pointer; moving from trigger to the tooltip center in 15 mouse steps made it disappear. It has no automatic “read-time” expiry, but Kobalte also hides it on relevant ancestor scroll. **The default hover-open wrapper is not hoverable**, the condition described by WCAG 1.4.13 and failure F95. Consequently these defaults are not evidence of satisfying all three 1.4.13 conditions. This is the observed/default behavior, not an audit of every custom style, controlled mode or tooltip use. [Spike] [K-tooltip] [WCAG-tooltip]

### Drawer / sheet inventory

There is **no Drawer/Sheet/bottom-sheet export or implementation in the published UI inventory**, and no Corvu dependency in its runtime dependency list. OpenCode's bottom sheet is **application-owned**, importing `@corvu/drawer@0.2.4`, not an `@opencode/ui` component. [U-package] [Drawer]

Corvu Drawer forwards Dialog behavior; its default Dialog is modal, `trapFocus: true`, `restoreFocus: true`, `closeOnEscapeKeyDown: true`, role dialog and `aria-modal`. It accepts initial/final focus elements. The app wrapper uses `side="bottom"`, supplies optional `finalFocusEl`, and the mobile-panel wrapper opts out of outside-focus dismissal during its transition. The app supplies an explicit **Close button with a localized accessible label**, so closing is not dependent on dragging. ## 5. Solid Virtual: focused rows and ARIA

**Yes: `rangeExtractor` can include an index outside the visible range.** The official API explicitly describes rendering sticky/header/footer indexes irrespective of visibility. The installed core's `getVirtualIndexes` calls the extractor; `getVirtualItems` returns the resulting measurement entries. It does not automatically know which row has DOM focus. [V-api] [V-source]

The fixed-height Solid spike tracked the focused index, returned a sorted union of `defaultRangeExtractor(range)` plus that index, and rendered with Solid `<For>`. With **100 × 32px** rows and a **128px** viewport, focusing row 1 then programmatically scrolling to 1,600px left `document.activeElement.id === "row-1"`; rendered indexes were **1, 49, 50, 51, 52, 53, 54**. This proves that composition can keep a focused row mounted; it does not establish that default range extraction, DOM keyed by position, data removal, or every adapter preserves focus. [Spike]

`scrollToIndex(index, {align: 'auto'|'start'|'center'|'end', behavior: 'auto'|'smooth'})` is a public API. Keyboard handlers can call it, but Virtual does not supply a list/grid keyboard model or focus the target row itself. With fixed heights, the target offset comes from measurements/estimates. [V-api] [V-source]

Virtual is headless: neither inspected adapter/core source emits row/list ARIA metadata. No dedicated `aria-rowcount`/`aria-rowindex` or `aria-setsize`/`aria-posinset` prescription was found in the inspected Virtual API docs. The authoritative general patterns are:

- WAI-ARIA APG's **grid/table properties**: `aria-rowcount` on table/grid/treegrid includes header rows; `aria-rowindex` on all represented rows is **1-based**, including headers. These describe total structure when not all rows are in the DOM. [V-aria-table]
- MDN/WAI-ARIA's **set-position properties**: `aria-setsize` and **1-based** `aria-posinset` belong on each represented item/option; `-1` expresses unknown total. They are not a replacement for grid/table row metadata and do not cause absent items to be rendered. [V-aria-list]

## 6. `content-visibility: hidden`, accessibility and inert

### Required semantics versus browser/tool observations

CSS Containment §4 requires skipped **contents** of `content-visibility: hidden` to be unavailable to find-in-page/tab navigation, nonfocusable/nonselectable; §4.6 explicitly requires omission from the accessibility tree. This is **not** the same as `auto`, which preserves access to skipped content in normal interaction. The property only applies where size containment can apply. Critically, skipping **contents** does not make the host itself inert: its own box/tab stop can remain, and Chromium's native AX tree retained the named host region in this fixture. [CV-spec] [CV-mdn] [Spike]

MDN compatibility data reports `hidden` support in Chromium **85+**, Firefox **125+**, Safari/iOS **18+**. Support metadata is not a guarantee of bug-free AX-tree updates. Historical AX bugs include Firefox **1793747**, fixed for 111 before default property enablement, and WebKit **292380**: Safari 18.4/TP217 did not reliably re-expose content after hidden→visible; fixed May 2025 at `294420@main`, reporter confirmed the fix. That WebKit fix includes a native accessibility test checking both normal and `display:contents` buttons. Current WebKit source explicitly includes `usedContentVisibility()==Hidden` in its hidden-style checks and invalidates AX children on changes. [CV-bcd] [CV-gecko] [CV-webkit]

**WebKit snapshot caveat:** Playwright 1.61.1's `isElementStyleVisibilityVisible` intentionally avoids WebKit `checkVisibility()` because of WebKit **264733** (unslotted content); its fallback checks `visibility`/details rather than `content-visibility`. Its ARIA snapshot therefore included the hidden WebKit child even though WebKit itself returned `checkVisibility() === false` and rejected tab/programmatic child focus. That is **not evidence of a native Safari AX leak**. Native WebKit accessibility capture and VoiceOver testing were not performed. Chromium's CDP tree independently confirmed actual exclusion there. [PW-hidden] [CV-webkit] [Spike]

### Is inert needed too?

For an **applicable block container's descendants**, `hidden` already has the required nonfocusable/AX-hidden semantics: `inert` is not a CSS-spec prerequisite, and the three-engine focus experiment needed no inert for descendants. But `hidden` can leave a focusable/named **host itself** in place; adding `inert` makes the **host and flat-tree descendants** noninteractive and excluded from the accessibility tree. They are different scopes, not synonymous hiding mechanisms. Unsupported/inapplicable CSS values cannot supply the specified exclusion; explicit inert has its own behavior independent of skipped rendering. No statement here asserts that all historic Safari versions have reliable dynamic AX updates. [CV-spec] [CV-inert] [Spike]

## Experiment details and limits

The throwaway fixture rendered three synthetic bars with `barY`, linear scales, `svgAnimation:false`, one named chart, one additionally described chart, and optional `tooltip: { use: tooltip }` definition configuration. It used the real Solid Chart, real UI Tooltip/Select/Popover/Dialog/Menu and DialogProvider, not stand-in DOM. No general-purpose CSS reset/theme or OpenCode app provider tree was added; component-local imported CSS was compiled by Vite. Tooltip geometry/hover was exercised with actual mouse movement. The service-opened Dialog included a real `[autofocus]` input; two reverse Tabs stayed within the dialog; Escape closed it; after 250ms the active element was body. Popover/Select/Menu focus observations were actual DOM focus checks, not inferred from their names.

Representative chart assertions:

```js
await page.locator("svg.ts-chart").first().focus();

await page.keyboard.press("End");
await page.keyboard.press("Enter");

// Callback log: ["focus:1", "focus:2", "focus:3", "select:3"]
const cdp = await page.context().newCDPSession(page);
const { nodes } = await cdp.send("Accessibility.getFullAXTree");
// Visible AX nodes included image Default chart and polite status x: 3 y: 30.

<input id="after" aria-label="After" />
```

Each run focused before, pressed Tab twice, recorded actual focus, attempted `secret.focus()`, inspected `secret.checkVisibility()`, and then added `host.inert=true` and repeated navigation. Chromium CDP confirmed the remaining host region and absent hidden descendants. The initial all-button fixture produced a different WebKit tab sequence because macOS restricts button/link tabbing; it was replaced by this input-based control before reporting the cross-engine comparison. This is a documented test correction, not a CSS focus leak.

No end-to-end dashboard/TanStack Start accessibility test; no real screen-reader spoken output or screen-reader shortcut interception; no shipping Safari/native WebKit AX-tree capture; no complete app command-palette runtime; no drawer browser exercise; no automated WCAG conformance claim. Scratch dependencies, generated bundles and logs were not added to repo packages or to the main working tree.
